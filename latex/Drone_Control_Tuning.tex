\section{Abstract}
This project focuses on the development of a tool for offline tuning of gyro controllers for FPV racing
drones based on the open-source firmware Betaflight. The quality of the gyro control loop has a direct influence
on flight stability, the suppression of disturbances such as prop wash and the agility of the drone. Until now,
rate controller tuning has mostly been performed through time-consuming trial and error. \par
The aim of the project is to develop a modular, open-source solution for offline tuning based on an existing
proof of concept. The code will be implemented in MATLAB, accompanied by a lightweight Python version and
supplemented with detailed Markdown documentation and examples on GitHub. The project aims to provide the
community with a simple way to efficiently optimise drone parameters and thereby improve flight performance.
\par
The results will be published in a public GitHub repository and documented in a report. In addition to the
software development, the project also includes practical work with FPV drones to validate the developed
methods.

\section{Introduction}
\label{Introduction}
First-Person-View (FPV) racing drones require precise and responsive control to achieve high flight stability, minimize disturbances such as propeller wash and maintain agility during rapid maneuvers. Proper tuning of the angular rate controllers is essential to this performance, as it directly determines how the drone reacts to pilot inputs and external influences. Until now, tuning these controllers has predominantly relied on iterative trial-and-error methods. This approach is both time-intensive and requires substantial piloting experience, thus presenting significant barriers for less experienced pilots.

Betaflight, an open-source firmware widely used in the FPV community, provides a flexible platform for configuring flight controllers. However, despite its popularity, efficient tuning remains a significant challenge. To address this, the present project builds upon an existing proof of concept for offline tuning of angular rate controllers using flight data and system identification techniques. The objective is to transform this concept into a robust, modular and open-source library that simplifies the tuning process.

The library is implemented in MATLAB and partially Python, providing tools for analyzing flight logs, estimating system dynamics and mainly controller parameters without requiring repeated flight tests. Comprehensive documentation is developed and published on GitHub to ensure accessibility for the FPV community. This documentation demonstrates the practical application of the tool and provides detailed technical background on the underlying methods.

Beyond software development, this project also encompasses the construction and flight testing of an FPV drone to validate the effectiveness of the proposed methods. By providing a structured, data-driven approach to tuning, this work aims to improve flight performance and reduce the barriers to achieving optimal control settings for both hobbyists and professionals.

This document is structured as follows: \autoref{sec:Theory} provides the theoretical foundations of control systems and signal processing relevant to the tuning process. \Cref{sec:ChallengesAndMethodologicalApproach} details the methodological challenges and solutions developed during implementation, including simulations, drone construction and the code migration from MATLAB to Python. \Cref{sec:Results} presents the results obtained from simulations and flight tests. Finally, \autoref{sec:DiscussionAndNextSteps} discusses the findings and outlines future work planned for continuation in the bachelor thesis.

\subsection{Initial Situation}
The open-source firmware Betaflight is the most popular platform for FPV racing drones and is continuously developed by a large community. The quality of the rate controllers is crucial for flight performance, as it enables stability, agility and effective suppression of disturbances such as prop wash.\par
Today, tuning of controller parameters is still largely performed by trial-and-error adjustments, a method that is time-consuming and often challenging for less experienced pilots. A proof of concept (developed by Michael Peter) already exists, which enables offline tuning of rate controllers using flight measurement data obtained from chirp signal excitation. However, the current implementation is based on MATLAB, which has limited access and therefore less common in the FPV-community. In addition, the proof-of-concept requires a certain level of technical knowledge to operate, which further complicates its practical use for many pilots. \par
As a result, the potential of data-driven controller tuning remains largely unused in everyday FPV practice. This creates a gap between academically established system identification and control design methods on the one hand, and the predominantly experience-based tuning approaches used by pilots on the other. Bridging this gap represents a key motivation for the further development of the existing proof of concept.

\subsection{Project Objectives}
The aim of this project is to further develop the existing proof of concept into an accessible and practical tool for tuning rate controllers on Betaflight-based FPV drones. The focus lies on transforming the prototype from a research-oriented MATLAB implementation into a solution that can be used by the wider community with minimal technical barriers. This includes designing a clean and modular software architecture, improving usability and integrating functions for importing, processing and analyzing flight data.
\par
In addition, the tool will be accompanied by comprehensive Markdown documentation, including explanations of key methods, usage instructions and practical examples to support new users. The implementation will serve as a foundation for future developments, such as extended analysis features or alternative controller designs. The overarching objective is to provide a reliable, data-driven workflow that replaces subjective trial-and-error tuning and enables verifiable control performance improvements.

This section provides an overview of the key concepts and methods used for the analysis and tuning of the Betaflight flight controller. It introduces the essential aspects of signal processing, control system identification and evaluation techniques that form the basis for optimizing controller performance. \subsubsection*{Betaflight Gyro Control System}

Based on the Betaflight source code, the gyro control system was reconstructed to obtain a detailed internal representation of the controller structure. Nevertheless, the simplified representation captures the essential structure required for analysis.

The control system consists of an inner and an outer control loop. In the inner loop, the derivative term is calculated directly from the gyroscope signal and is used to improve damping by shaping the dynamic response.

\subsubsection*{Chirp Concept}
A chirp is an input signal that sweeps continuously over a defined frequency range (from low to high frequency).
This signal excites the system at multiple frequencies in one run, thus allowing the observation of the frequency response and step response,
which form the foundation of controller tuning.
Mathematically, a chirp signal can be represented as a sinusoidal wave with instantaneous frequency that varies linearly or exponentially with time \parencite{bf_chirp}.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{./Images/Theory/chirp_signal.png}
	\caption{Chirp signal example}
	\label{fig:chirp}
\end{figure}

\subsubsection*{Chirp Implementation in Betaflight}
For drone flight controller tuning, an exponential frequency sweep is employed.
This choice is motivated by the dominant low-frequency dynamics of multirotor systems, where low frequencies exhibit more predictable responses.
The exponential sweep allocates proportionally more time to higher frequencies, providing better resolution of system behavior in that range.
Additionally, multirotor vibration resonances are typically spaced logarithmically,
making exponential sweeps particularly well suited for efficient excitation across the frequency range.

The measurement process involves three main steps:
\begin{enumerate}
	\item \textbf{Signal injection:} The chirp signal is added to the pilot's stick input, forming the composite setpoint for the PID controller.
	\item \textbf{System response:} The drone attempts to track this rapidly varying setpoint. The motors react, causing the drone to oscillate at frequencies corresponding to the instantaneous chirp frequency.
	\item \textbf{Data logging:} Betaflight's Blackbox feature records high-resolution data from the gyroscope and motor outputs throughout the chirp excitation. This data captures the system response to control inputs across the entire frequency range.
\end{enumerate}

The recorded log file, containing both the input chirp and the corresponding gyroscope response,
is then used for offline analysis to determine the frequency response of the system.
However, to ensure reliable frequency response estimation, the chirp signal must first be properly conditioned before injection into the control loop.

\subsubsection*{Lag Filter for Chirp Input Shaping}

Before the chirp signal is injected into the control loop, it is conditioned by a filter to address the differentiating behavior of the controller effort at low frequencies. This differentiating characteristic causes rising gain at low frequencies, which would lead to excessive motor response at the start of the chirp sweep and potentially cause saturation, compromising the quality of system identification data. The filter reduces low-to-mid frequency components of the chirp signal before injection, such that the combined response produces approximately uniform excitation across the frequency range.

The filter is configured with a pole at 3 Hz and a zero at 30 Hz. This configuration corresponds to the transfer function
\begin{equation}
	H(s) = \frac{1 + s/\omega_z}{1 + s/\omega_p}
\end{equation}
where $\omega_z = 2\pi \cdot 30$ rad/s and $\omega_p = 2\pi \cdot 3$ rad/s represent the zero and pole frequencies respectively. The pole introduces the lag component by creating magnitude reduction at frequencies above its cutoff frequency. The zero limits this reduction by introducing magnitude amplification at frequencies above its cutoff frequency. However, since the pole frequency is lower than the zero frequency, the pole's contribution dominates throughout the primary control bandwidth, resulting in a net lag filter. It is important to note that in the Betaflight implementation, the pole frequency ($\omega_p$) must not be set higher than the zero frequency ($\omega_z$), as this would create a lead filter that amplifies high frequencies and could potentially damage the motors.

	\caption{Chirp signal example with Lag Filter}

\end{figure}

\subsubsection*{Data Import and Preprocessing}
To analyze Betaflight Blackbox logs effectively, the recorded data must first be imported and preprocessed to ensure correct scaling, structure and suitability for further analysis. Each log consists of a header containing essential metadata, such as filter settings PID values and a data block with the recorded signals. Both components are required for correct interpretation of the flight data.

To reduce computational effort, the raw CSV log files are converted into the faster MATLAB \texttt{.mat} format, allowing for significantly shorter loading times. During this step, signal names are automatically mapped to their corresponding data columns, which simplifies the identification and use of individual signals in further analyses \parencite{bf_LoadData}. Betaflight's High Resolution Mode scales selected signals by a factor of ten to optimize storage and reduce numerical rounding errors. These signals are therefore rescaled to their original values during preprocessing to ensure accurate results \parencite{bf_UnshigRes}.

Finally, the time information, originally stored as a microsecond counter, is converted into a uniform time base. By evaluating the time differences between samples, irregular sampling caused by dropped frames or variations in the effective sampling rate can be detected. Proper handling of the time data is essential for reliable frequency analysis and controller tuning \parencite{bf_TimeConv}.

\subsubsection*{Spectrum and Spectrogram Analysis}

Spectrum and spectrogram analysis are powerful tools for understanding how a system behaves across different frequencies. The spectrum decomposes a signal into its frequency components, indicating which frequencies are dominant and which are attenuated. This allows resonances, noise contributions and the effectiveness of filtering stages to be identified.

The recorded data logs provide two types of gyroscope signals: the signal \texttt{gyroADC} and the signal \texttt{gyroUnfilt}. The difference between these two signals is that the \texttt{gyroADC} signal has already passed through the internal Betaflight filtering stages, whereas the \texttt{gyroUnfilt} signal represents the raw data directly measured by the gyroscope sensor without any filtering applied, as illustrated in \autoref{fig:gyro_filtered_vs_unfiltered}.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.7\linewidth]{Images/Theory/Control_Gyro.png}
	\caption{Open loop block diagram gyro}
	\label{fig:gyro_filtered_vs_unfiltered}
\end{figure}

Transforming both signals into the frequency domain reveals the effect of the internal filters on the signal content. The filtered signal shows reduced high-frequency noise and attenuated frequency components, while the unfiltered signal contains stronger high-frequency noise and structural resonances.\parencite{bf_Spectra}

The spectrogram extends this analysis by showing how the frequency content of the gyroscope signal changes with throttle. The signal is divided into overlapping segments, transformed using an FFT and averaged within discrete throttle bins \parencite{bf_Spectrogram}.

This representation helps to understand how resonances, noise levels and dominant frequency components change with throttle, giving insight into the system dynamics under different flight conditions.


\subsubsection*{Estimation of Frequency Response Including Rotational Filtering}

To estimate the frequency response of a system from measured input and output signals, the data must first be transformed into the frequency domain. This is achieved using the Fast Fourier Transform (FFT). The frequency response is then obtained by dividing the Fourier transform of the output signal by that of the input signal:

\begin{equation}
	G_{xy}(\omega) = \frac{\mathrm{FFT}(y)}{\mathrm{FFT}(x)}
\end{equation}

In practical applications, measurement data is often disturbed by noise, which can significantly distort the frequency response estimation. As illustrated in \autoref{fig:system_noise}, noise is added to the system between the input signal \(u(t)\) and the output signal \(y(t)\). This noise may originate from sensor inaccuracies, environmental disturbances, or electronic interference. If not properly handled, it can lead to unreliable or misleading results. To mitigate this effect, the program applies a dedicated filtering routine, implemented in the function \texttt{apply\_rotfiltfilt}.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.55\textwidth]{Images/Theory/Freq_Blockschalt.png}
	\caption{Block diagraml including measurement noise}
	\label{fig:system_noise}
\end{figure}

To improve the robustness of the frequency response estimation, a rotational filtering approach is used. In this method, the output signal is shifted to the baseband, filtered and then shifted back to its original frequency range. The frequency shift is achieved by multiplying the signal with a complex exponential corresponding to the instantaneous chirp frequency:

\begin{equation}
	y_{\mathrm{rot}}(t) = y(t) \cdot e^{-j 2 \pi f_{\mathrm{chirp}}(t) t}
\end{equation}

After shifting the signal to baseband, a zero-phase filter is applied to remove unwanted frequency components while preserving the phase information of the signal. This step is essential for reducing noise without distorting the underlying system dynamics. The filtered signal is then shifted back to its original frequency range \parencite{bf_ApplyRot}.

Subsequently, the frequency response is estimated using the filtered output signal within the function \texttt{Estimate Frequency Response}. The signal is divided into overlapping segments, as illustrated in \autoref{fig:segmentation}. The FFT is computed for each segment and the resulting spectra are averaged to obtain a smooth and reliable estimate of the frequency response \parencite{bf_estfreqresp}.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.9\textwidth]{Images/Theory/segmentation.png}
	\caption{Segmentation of a signal into overlapping windows}
	\label{fig:segmentation}
\end{figure}

\subsubsection*{Transfer Function Estimation}

In a closed-loop control system, the plant is the physical system that we want to control, for example, the movement of a drone.
To tune a controller, we need to understand how the plant behaves. However, when the system is running in closed-loop, this becomes difficult.
The output is fed back through the controller and continuously changes the input signal. Because of this, the input is no longer an independent excitation but instead already contains the controller reactions and disturbance effects.

If we try to measure the transfer function directly from input to output in this situation, the result will not represent the true behavior of the plant.
Instead, it will show a combination of the plant dynamics, the controller dynamics and the feedback loop.
\autoref{fig:closedloop} shows a simplified closed-loop structure.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.65\textwidth]{Images/Theory/Control_Loop_easy.png}
	\caption{Simplified closed loop system}
	\label{fig:closedloop}
\end{figure}

To overcome this problem, we use the known relationships between the different transfer functions in the closed-loop.
From the measurement data we compute

\begin{equation}
	G_{yr}(\omega) = \frac{\mathrm{FFT}(y)}{\mathrm{FFT}(r)}
	= \frac{C(\omega)\,P(\omega)}{1 + C(\omega)\,P(\omega)}
\end{equation}

\begin{equation}
	G_{ur}(\omega) = \frac{\mathrm{FFT}(u)}{\mathrm{FFT}(r)}
	= \frac{C(\omega)}{1 + C(\omega)\,P(\omega)}
\end{equation}

By dividing the two expressions, the controller cancels out and we obtain an estimate of the plant transfer function:

\begin{equation}
	P(\omega) = \frac{G_{yr}(\omega)}{G_{ur}(\omega)}
\end{equation}

This allows us to reconstruct the plant transfer function \(P(\omega)\) from closed-loop measurement data without opening the control loop during the experiment \parencite{bf_Transfun}.


\subsubsection*{Closed-Loop Calculation}

After determining the plant transfer function, the next step is to analyze the behavior of the overall system when a controller is applied. This is achieved by evaluating the closed-loop transfer functions, which describe the system response, disturbance sensitivity, disturbance rejection capability and the required controller effort. These measures provide valuable insights into the stability, robustness and performance of the controlled system.

As an example, the closed-loop configuration shown in \autoref{fig:closed_loop} is analyzed.

\begin{figure}[h]
	\centering
	\includegraphics[width=0.65\textwidth]{Images/Theory/Control_Loop_easy.png}
	\caption{Simplified closed loop system}
	\label{fig:closed_loop}
\end{figure}

The closed-loop transfer function from the reference input to the output is given by
\begin{equation}
	G_{yr}(\omega) = \frac{C(\omega) P(\omega)}{1 + C(\omega) P(\omega)}
\end{equation}

The sensitivity function, which describes how sensitive the system output is to disturbances and model uncertainties, is defined as
\begin{equation}
	S(\omega) = \frac{1}{1 + C(\omega) P(\omega)}
\end{equation}

The compliance function, representing the system response to disturbances acting on the plant, is given by
\begin{equation}
	SP(\omega) = P(\omega) \cdot S(\omega)
\end{equation}

Finally, the controller effort describes the influence of the reference input on the controller output and is defined as \parencite{bf_closeloop}
\begin{equation}
	SC(\omega) = C(\omega) \cdot S(\omega)
\end{equation}

\subsubsection*{Compensation of the I-Term}
The integral term of a PID controller is used to compensate for steady-state errors by integrating the control error over time. In flight control systems, this helps to counteract constant disturbances such as motor imbalances or aerodynamic effects. During fast stick movements or aggressive maneuvers, however, the integral term can accumulate too much error.

In these situations, the accumulated I-term no longer represents a disturbance but instead opposes the intended motion. When the maneuver ends, this can lead to overshoot, bounce-back effects, or slow settling of the system.

To reduce these effects, Betaflight uses a feature called I-Term Relax. This mechanism temporarily limits the integration of the I-term when rapid changes are detected. Depending on the configuration, these changes are identified either from the control setpoint or from the measured gyroscope signal. When the detected change exceeds a defined threshold, the I-term integration is reduced or paused.

This allows the controller to respond quickly to fast pilot inputs while preventing excessive buildup of the integral term. During slower movements and steady operation, normal integration is restored. As a result, I-Term Relax improves flight behavior by reducing overshoot and bounce-back while maintaining good disturbance rejection.

For analysis and controller tuning, the effect of I-Term Relax must be considered, as it modifies the controller behavior depending on the current flight conditions.
\begin{figure}[h]
	\centering
	\includegraphics[width=0.7\textwidth]{Images/Theory/Control_Loop_Iterm.png}
	\caption{Simplified closed loop system with I-term Relax}
	\label{fig:I_term}
\end{figure}

The measured controller transfer function is compared with an analytically derived controller transfer function. The effect of the I-Term Relax algorithm is therefore included implicitly in the measurement-based result.

To this end, a compensation factor is defined as the ratio between the measured PI controller transfer function and its analytical counterpart:
\begin{equation}
	C_{\mathrm{PI,com}}(\omega) = \frac{C_{\mathrm{PI}}(\omega)}{C_{\mathrm{PI,ana}}(\omega)}
\end{equation}

This frequency-dependent compensation factor represents the combined influence of effects that are not explicitly modeled, including the impact of I-Term Relax. The factor is further applied to both the original analytical PI controller and the newly designed PI controller:
\begin{align}
	C_{\mathrm{PI,ana,new}}(\omega) & = C_{\mathrm{PI,ana}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega) \\
	C_{\mathrm{PI,new,new}}(\omega) & = C_{\mathrm{PI,new}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega)
\end{align}

The resulting compensated controller transfer functions are then reinserted into the closed-loop system for further analysis and evaluation \parencite{bf_compITerm}.

\subsubsection*{Step Response}
The step response provides a direct view of how the system reacts to sudden changes in the input signal. Unlike the transfer function, which describes the system behavior in the frequency domain, the step response is defined in the time domain and therefore offers intuitive insight into the transient behavior of the system.

To obtain the step response, the closed-loop transfer function must be transformed back into the time domain. This is achieved by applying the inverse Fourier transformation to the output spectrum
\begin{equation}
	y(t) = \mathcal{F}^{-1}\{Y(\omega)\}
	= \mathcal{F}^{-1}\{G_{yr}(\omega)\cdot R(\omega)\}
\end{equation}

Using the convolution theorem, this expression can be interpreted in the time domain as a convolution of the system's impulse response $g_{yr}(t)$ with the input signal $r(t)$:
\begin{equation}
	y(t) = (g_{yr} * r)(t)
	= \int_{0}^{t} g_{yr}(\tau)\, r(t-\tau)\, d\tau
\end{equation}

For a step input, this convolution illustrates how the system accumulates the effect of its impulse response over time, leading to the characteristic shape of the step response \parencite{dortClosedLoopAnalysis}.

At low frequencies, the integral term causes a slope of $-20\,\text{dB/decade}$
\begin{equation}
	|C_I(\omega)| = \frac{K_i}{\omega} = \frac{10}{\omega}
\end{equation}

The corresponding lower corner frequency is
\begin{equation}
	\omega_{k,I} = \frac{K_i}{K_p} = \frac{10}{100} = 0.1\,\text{rad/s}
\end{equation}

The derivative term causes the slope of $+20\,\text{dB/decade}$ at high frequencies with
\begin{equation}
	|C_D(\omega)| = K_d\,\omega = 10\,\omega
\end{equation}

Accordingly, the upper corner frequency is given by
\begin{equation}
	\omega_{k,D} = \frac{K_p}{K_d} = \frac{100}{10} = 10\,\text{rad/s}
\end{equation}

This example also shows that changing the integral and derivative gains shifts the position of the slopes in the Bode plot. A larger integral gain moves the low-frequency slope towards higher frequencies, while a larger derivative gain moves the high-frequency slope towards lower frequencies. In this way, the shape of the frequency response can be adjusted to the desired system behavior.

\subsubsection*{Filter tuning}
Before we start tuning the PID controllers, we need good filtering to have clean signals to work with. The general aim here is to use as little filtering as possible because too much filtering causes delay in the system. However, no quadcopter build is perfect, so at least some filtering is necessary in order to achieve a well-tuned system.

After running the program in MATLAB and importing a log file, you can see in the command window which filter and PID settings were used during that flight. Our tool, in its current state, doesn't copy these values to the code automatically, so the first step is to copy the settings from the command window to the correct position in the code.

We then start by looking at the spectrograms and spectra figures to assess the effectiveness of the current filtering. It is important to note that the spectra and spectrogram plots only show the data recorded in the loaded log file. Changing filter settings in the code does not affect these plots, as they reflect the settings that were active during the flight. To see the effect of any changes, a new flight must be performed and logged with the updated settings.

The \textbf{spectra} in \autoref{fig:Spectra_tuning} shows the frequency composition of the gyro signals.
Peaks in this plot point to vibration sources at specific frequencies.
When we analyze this plot, we look for three main things:
\begin{itemize}
	\item \textbf{Resonance Peaks:} If all three axes show a peak at the same frequency, it usually means there is a resonance in the frame or due to a poorly fixed component. This can be fixed with a specific notch filter or by attaching the loose parts properly.
	\item \textbf{Noise:} A high noise level indicates general vibration issues. By adjusting the D-term low pass filter, you can counteract this. Clean lines in the plot show that the filtering is working well.
	\item \textbf{Axis Sum:} The axis sum shows the overall vibration level across all gyro axes. A properly filtered signal drops quickly after the motor frequencies (after around 600 Hz) and remains low, indicating effective suppression of high-frequency noise and resonances.
\end{itemize}

\begin{figure}[H]
	\centering
	\includegraphics[width=0.85\textwidth]{./Images/Tuning_OvershootExpress/Spectra.png}
	\caption{Spectra}
	\label{fig:Spectra_tuning}
\end{figure}

We can see in this figure that our filter settings work well. The filtered signals have very little noise (smoother lines) and no large resonances. Only the yaw axis has a small peak around 550 Hz, which is acceptable. The axis sum drops nicely and stays low after about 600 Hz, approximately where the motor frequencies end. This shows the drone is running smoothly with vibrations under control. 
The vibrations are also visible in the \textbf{spectrogram} plots in \autoref{fig:Spectrograms_tuning}.
Here, frequencies are plotted against thrust level and the color shows the signal intensity. Red equals much vibration, blue equals little vibration.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{./Images/Tuning_OvershootExpress/Spectrograms.jpg}
	\caption{Spectrograms}
	\label{fig:Spectrograms_tuning}
\end{figure}

\textbf{Vertical lines} in the spectrogram indicate vibrations at fixed frequencies that do not change with thrust. These usually come from frame resonances or loose components. Such resonances can be removed with static notch filters, but because they are fixed at a single frequency, they must be used carefully. For more robust suppression, especially when frequencies shift due to bent props or changing load conditions, a dynamic notch filter is usually the better choice. Also to mention is, that static notch filters should only be applied, when the same resonances appear in all three axes at the same frequency.

\textbf{Diagonal lines} show vibrations that change with motor speed, such as propeller noise. Using the RPM Filter, these propeller vibrations can be filtered out quite well. This filter uses real-time RPM telemetry data to place notch filters exactly on the fundamental and harmonic frequencies of each motor. As propeller vibrations are directly proportional to motor RPM, this approach eliminates noise at its source instead of relying on fixed or dynamic estimation. In our case, we kept the RPM filter with the default settings. We used \textbf{three-bladed} propellers, so the filter has been set to \textbf{three harmonics}. As we can see in \autoref{fig:Spectrograms_tuning} under the filtered plots, the RPM filter removes the diagonal lines effectively.

\textbf{Aliasing}\\
When sampling a signal that contains frequencies higher than half of your sampling rate, aliasing can occur. This would make high-frequency content appear as lower frequencies, corrupting the measurement data. To avoid this, we applied a PT1 low-pass filter with a cutoff frequency not greater than the sampling frequency divided by two. As we use a 2 kHz logging frequency, we set the cutoff to 800 Hz as a conservative choice.
If aliasing occurs on your drone, it appears in the spectrogram as diagonal lines going down as you move to higher frequencies.

\textbf{Dynamic notch filter}\\
The dynamic notch filter automatically finds and removes mechanical motor noise with the highest amplitude for each axis. The standard setting here is 2 notches from 100 to 600 Hz. Through testing, we found that changing the notch filter count from two to three provided better filtering. We can see in \autoref{fig:Spectrograms_tuning} that the filtered plots don't show any diagonal lines anymore. It is important to keep in mind that adding more notches also adds delay to the system. However, for the robustness of our tune, this trade off can be turned in favor of compensating external influences.

\textbf{D-term low-pass filter}\\
The D-term in a PID controller amplifies high-frequency gyro noise. So this filter controls how much noise is fed back into the control loop. If too much noise passes through, the D-term causes rapid micro-oscillations in the motors, leading to overheating and potential hardware failure.
For our initial flight, we configured a PT3 (third-order) filter with a cutoff of 100 Hz. We chose this filter because PT3 has a much steeper slope than a standard first- or second-order filter. This allows us to aggressively suppress high-frequency noise while minimizing delay in the lower frequencies where the actual flight control happens. The 100 Hz cutoff served as a conservative starting point and worked well. In further tuning, this value can be increased to improve responsiveness while keeping the motors cool. Through trial and error, the value can be increased as long as the motors don't heat up too much during flight.

\textbf{Yaw low-pass filter}\\
The yaw low-pass filter smooths the gyroscope signal by ignoring high-frequency noise. Since the yaw axis typically experiences less mechanical vibration than roll and pitch, the filter can often be configured less aggressively without compromising signal quality.
For our setup, we retained the default Betaflight settings, as they provided good noise suppression without creating unnecessary delay.

Further information about spectra and spectrograms can be found \href{https://github.com/InsaneBroccoli/bf_controller_tuning/blob/main/markdown/Spectrum_Spectrogram}{here}. Also consider looking at the \href{https://www.betaflight.com/docs/wiki/configurator/pid-tuning-tab}{Betaflight wiki page} for more information about Betaflight filters.

\textbf{Gang of Four}\\
The Gang of Four is a standard set of four transfer functions that together fully characterize a feedback control system. These four plots represent the Sensitivity (S), Complementary Sensitivity (T, Bode plot), Controller Effort (SC) and Compliance (SP). By analyzing these plots, we can assess the stability of the drone, its ability to follow commands, its response to external disturbances and the workload on the motors, all in one comprehensive view.

During our tuning process, we found these plots to be invaluable for diagnosing and improving the drone's performance. While all four plots provide useful information, we focused primarily on three of them:
\begin{enumerate}
	\item Sensitivity (S):
	      This plot shows how the system reacts to noise and reference commands. The peak value is a key indicator of stability. In our experience, a peak below 6 dB is ideal for a well-damped system. Higher peaks suggest the drone might oscillate or become unstable, especially during aggressive maneuvers. We noticed that reducing the peak often required balancing stability with responsiveness, as overly conservative settings could make the drone feel sluggish.
	\item Controller Effort (SC):
	      This plot indicates how much work the controller is doing to maintain stability and follow commands. High effort at higher frequencies usually means the system is reacting to sensor noise rather than real disturbances. This can lead to unnecessary motor activity, overheating and wear. During tuning, we found that adjusting the D-term gains and optimizing filters helped reduce high-frequency effort while keeping the drone responsive.
	\item Compliance (SP):
	      Compliance measures how much external disturbances, like wind or propwash, affect the drone's motion. Lower compliance means the drone resists disturbances more effectively. We observed that increasing the P-term gains improved disturbance rejection, but setting them too high caused oscillations during rapid throttle changes. Finding the right balance was critical for maintaining both stability and responsiveness.
\end{enumerate}

In our experience, the Gang of Four plots provided a clear and structured way to evaluate the effects of each tuning adjustment. For example, after making changes to the PID gains, we could immediately see how these changes impacted stability, motor effort and disturbance rejection. This iterative process allowed us to fine-tune the system with confidence, ensuring that the drone performed well under a variety of conditions.

\subsubsection*{PID Tuning Summary}
Our tuning objective was to achieve a fast step response without overshoot while maintaining good disturbance rejection and stability margins. It is important to note that there is no universally perfect tune. Settings depend heavily on pilot preferences. Racing pilots typically prefer aggressive, responsive tuning for competitive performance, while freestyle pilots may prioritize smoothness and flight feel. We focused on achieving robustness and a step response without overshoot. Robustness is practical in this case because it handles scenarios such as slightly bent propellers, a battery positioned off-center, or additional components such as cameras mounted on the drone. It should also be mentioned that the axes roll and pitch should be tuned as similarly as possible. This is because symmetrical tuning makes the drone more intuitive to pilot. When both axes respond identically to stick inputs, the drone behaves predictably during combined maneuvers, making control feel natural.

The tuning process involved iteratively adjusting PID gains in MATLAB while monitoring both the step response and Gang of Four plots side by side. We found and used an online \href{https://www.luisllamas.es/en/pid-controller-simulator/}{PID simulator} as a guide to build intuition for how P, I, and D values affect system behavior. For the step response, we aimed for a fast rise time with minimal or no overshoot and a smooth curve without oscillations. On the Gang of Four side, we wanted the sensitivity peak to stay below 6 dB for good stability margins, low compliance across the control bandwidth for effective disturbance rejection, and reasonable controller effort to avoid amplifying sensor noise. All transfer functions should show smooth, rounded shapes without sharp resonances that indicate problematic dynamics. Once we were satisfied with the curves and their shapes, we could take the P, I, and D values for each axis from the command window in MATLAB and set them via the Betaflight configurator to the drone.

\subsection{Decoding Betaflight Blackbox Logs}
\subsubsection*{Purpose}
Currently, to obtain a usable Blackbox log from Betaflight, pilots rely on the Betaflight Explorer.
This is a reliable tool but lacks convenience if the tuning tool is used iteratively since you have to visit the Explorer every time you want to download a new log.
To improve this workflow, we tried to make use of the existing open-source blackbox decode tool.

\subsubsection*{Blackbox Decode Tool}
The \href{https://github.com/betaflight/blackbox-tools/}{blackbox decode tool} is a C-based command-line utility designed to convert Betaflight Blackbox log files from their proprietary binary format into more accessible formats such as CSV.
It offers similar core functionality to the Betaflight Blackbox Explorer but is intended for users who prefer command-line tools or need to automate log processing tasks.\par

However, integrating blackbox decode into our project presented several challenges.
The most obvious issue is the absence of header information by default.
While this can be addressed by using the "--save-headers" flag, the format of these headers differs from that used by the Betaflight Explorer.
This discrepancy is manageable, as we could adapt our data import functions to handle both formats.\par

A more significant problem is the presence of numerical differences in the decoded data.
When comparing logs decoded with blackbox decode to those processed with Betaflight Explorer, the resulting datasets differ structurally and semantically in several critical ways.
Specifically, the blackbox decode stores the vehicle attitude as Euler angles in degrees, whereas the Explorer provides quaternion-like components.
With priority set on other tasks, we decided to set aside the integration of blackbox decode for now.

\subsubsection*{Object-Oriented vs. Functional Approach}
At this stage, we discussed whether to implement the entire project using object-oriented programming (OOP) or stick to a modular,
function-based approach. Initially, we considered OOP as a challenge since most of us were not very experienced with it.
We started writing some components as classes but quickly realized, OOP did not improve readability in certain context. This made us reconsider.
Our conclusion was to use OOP selectively—only for parts that benefit from reuse and encapsulation, such as data loading and plotting,
while keeping the rest function-based for simplicity. This hybrid approach allowed us to maintain flexibility without overcomplicating the design.

After several attempts, we agreed on the following principles:

\begin{itemize}
	\item A main script (main.m) for user input, figure selection, filter settings and PID tuning
	\item A core class to handle all calculations (essentially the logic from the proof of concept, but without plotting)
	\item A plot utilities class to centralize all plotting functions for consistency

The reason: we had created a "god class", which limited flexibility. For example,

The program was also slow. All calculations were performed every time the user changed something.
We wanted to improve the speed by only recalculating what was relevant for each specific user input change.

\subsubsection*{Final Structure Concept}
Based on this feedback, we decided to split this god class into three classes.
The \texttt{flight\_analyzer} class handles frequency-domain analysis and vibration characterization.
Its core responsibility is performing spectral analysis on flight log data to identify resonance frequencies and assess filter effectiveness.
It computes the power spectral density of gyro signals (both filtered and unfiltered) and generates spectrograms showing
how vibration frequencies vary with throttle levels across all three axes (roll, pitch, yaw).
This analysis is essential for identifying noise sources, evaluating filtering strategies and optimizing drone stability during tuning.
The \texttt{flight\_data} class is responsible for loading, parsing and managing flight log data.
It provides methods to extract relevant information from Blackbox logs, such as gyro and motor data and prepares this data for analysis.
The \texttt{gyro\_ctrl\_tuning} class focuses on tuning the PID controllers for the drone's flight.
It uses the results from the frequency response and spectral analysis to adjust the PID parameters, aiming to optimize the drone's flight characteristics.
The \texttt{plot\_utils} class remains responsible for visualization and graphical representation of all analysis results.
Unlike the previous approach, this class is now more flexible and reusable. It can be used independently to generate plots from pre-calculated data,
making it suitable for users who only want to visualize spectrograms, frequency responses, or step responses without running the full analysis pipeline.
This modularity allows the plotting functionality to be easily adapted for different visualization needs and integrated into other workflows.

\subsection{Conversion from MATLAB to Python}

To make the project more accessible to the FPV community, we decided to migrate the existing MATLAB codebase to Python.
The first step was to select suitable Python libraries that offer similar functionality to MATLAB while maintaining code efficiency and readability.
After evaluating several options, we chose the following libraries:
\begin{itemize}
	\item \textbf{NumPy}: For numerical operations and array manipulations, analogous to MATLAB's matrix operations.
	\item \textbf{SciPy}: For scientific computing tasks, including signal processing functions comparable to MATLAB's capabilities.
	\item \textbf{Matplotlib}: For plotting and visualization, providing features similar to MATLAB's plotting tools.
	\item \textbf{Pandas}: For data manipulation and analysis, useful for handling tabular data as in MATLAB tables.
	\item \textbf{Control Systems Library (control)}: For control system analysis and design, offering functions equivalent to MATLAB's Control System Toolbox.
\end{itemize}
We selected Python version 3.12, as it is well-supported and compatible with the required libraries.
To validate these choices, we developed a prototype script that implements the core functionalities needed for the Drone Tuning Tool.
The script loads flight log data from CSV files, parses and caches the data efficiently and extracts relevant signals such as setpoints and gyro measurements.
NumPy and Pandas are used for numerical and tabular data handling, while SciPy provides signal processing utilities for windowing and frequency analysis.
The Control Systems Library is employed to estimate the system's frequency response and step response from flight data, replicating MATLAB's identification routines.
Matplotlib is used for visualizing raw signals, chirp responses and system characteristics.
The modular structure, including custom data classes and caching, ensures fast and reproducible analysis.
This approach demonstrates that Python and its scientific libraries are suitable replacements for MATLAB in the drone tuning workflow.
While Pandas is not strictly necessary for the prototype, it simplifies data handling and improves code readability.
However, to minimize dependencies and ensure cross-platform compatibility, we may consider removing Pandas in the final implementation.
The flexibility of Python also allows for easier integration with other tools and automation of data processing tasks, which is beneficial for large-scale log analysis.

\subsection{Python in MATLAB}

In our initial porting attempt, we utilized MATLAB's built-in functionality to execute Python code directly from within the MATLAB environment.
While this approach allowed us to access Python libraries, it introduced some challenges.
One major issue was the frequent need for unit conversions between MATLAB and Python data types, which often led to  bugs and inconsistencies.
Additionally, we encountered differences in the implementation of certain algorithms, such as varying scaling conventions in the state-space representation of transfer functions.
These discrepancies complicated the integration process and made it difficult to ensure consistent results across both platforms.
Managing library dependencies and Python environments within MATLAB also proved cumbersome, especially when working across different operating systems or MATLAB versions.
As a result, this method proved unreliable for our project's requirements.
We decided to pursue a native Python implementation to avoid these issues and streamline the development workflow.

\subsection{Transferring the MATLAB Library to Python}

The core functionality of the Drone Tuning Tool resides in its library functions.
To ensure that the Python implementation is both reliable and consistent with the original MATLAB code, we systematically transferred each library function from MATLAB to Python.
For functions with simple numerical outputs, we used \texttt{np.testing.assert\_allclose} with appropriate absolute and relative tolerances, saving the function inputs and outputs from MATLAB and comparing them with the Python implementation.
For more complex functions, such as those involving state-space outputs, we developed dedicated test scripts to compare the behavior of the MATLAB and Python versions across a range of scenarios.

The initial validation process was conducted using flight data from a single test flight.
While several core functions successfully passed the comparison tests with the MATLAB reference implementation, some functions still require further refinement.
Specifically, the functions \texttt{apply\_rotfiltfilt} and \texttt{downsample\_frd} exhibit deviations that exceed the specified tolerance thresholds when compared to their MATLAB counterparts.
Additionally, \texttt{calculate\_transferfunctions} requires revision in the dynamic gyro low-pass filter configuration, as the current implementation produces runtime errors under certain conditions.

For the ongoing development, a comprehensive testing framework is planned that will validate all library functions against flight data from multiple test flights.
This extended validation will provide a more robust assessment of the Python implementation's reliability and help identify edge cases that may not have been apparent in single-flight testing.
The systematic transfer and validation process established so far provides a solid foundation for completing the migration and ensuring consistency between the MATLAB and Python implementations in future work.

\section{Results}
\label{sec:Results}

The existing proof-of-concept implementation was restructured into a modular codebase consisting of four distinct classes: \texttt{flight\_data} for Blackbox log management, \texttt{flight\_analyzer} for frequency-domain analysis and \texttt{gyro\_ctrl\_tuning} for system identification and controller analysis and \texttt{plot\_utils} for visualization. Comprehensive technical documentation in Markdown format was published on GitHub, covering data import, spectral analysis, frequency response estimation, transfer function reconstruction, filter design and plot interpretation.

Five simulation environments were developed to understand the proof-of-concept code and the methods applied within it. These included a Simulink model of the Betaflight control architecture with inner and outer control loops, all filter types and a simplified plant model that closely matched experimental behavior, a PID controller characteristics simulation, a frequency response estimation simulation comparing FFT, Welch and rotational filtering approaches, a spectral analysis simulation demonstrating windowing effects and a spectrogram generation simulation showing throttle-dependent vibration mapping. These simulations established an understanding of control theory and signal processing techniques required for the analysis workflow.

A three-inch FPV drone was constructed using an aosmini frame, integrated flight controller stack, twelve-pole motors and three-bladed propellers. The flight controller was flashed with Betaflight version 2025.12.0-RC1 for chirp mode access. Experimental tuning through iterative chirp flights and offline analysis successfully eliminated motor-induced vibrations and achieved step responses with minimal overshoot. The sensitivity function peak remained below 6 dB across all axes, ensuring adequate stability margins. Flight testing confirmed improvements in propwash handling and maneuver precision compared to default parameters.

Python migration was partially completed. Core library functions including frequency response estimation, spectral analysis, filter design and closed-loop calculations were transferred and validated against MATLAB implementations. Three functions require refinement: \texttt{apply\_rotfiltfilt} exhibits maximum differences of 0.024 absolute and 0.6\% relative in 0.2\% of data points, \texttt{downsample\_frd} shows systematic deviations across all frequencies and \texttt{calculate\_transferfunctions} produces runtime errors in dynamic gyro low-pass filter configuration. A validation framework using exported MATLAB test data enables systematic comparison.

\section{Discussion and Next Steps}
\label{sec:DiscussionAndNextSteps}

\subsection{Discussion}

The primary objective of this project was to establish a solid foundation for continued development during the bachelor thesis rather than to deliver a production-ready tool. This foundational focus proved essential, as it enabled the team to develop the necessary expertise in both control theory and practical flight operations before attempting more advanced implementations.

The restructuring of the existing proof-of-concept code into a modular architecture represents a significant technical achievement. The new class-based structure separates concerns effectively, with distinct components for flight data management, frequency-domain analysis and controller tuning. This separation not only improves code maintainability but also enables independent development of individual modules during future work. The systematic organization of library functions and the introduction of object-oriented design patterns will facilitate rapid implementation of additional features in the bachelor thesis.

Beyond the software architecture, the project required substantial acquisition of domain knowledge. Understanding the Betaflight control system architecture, including the interaction between filter stages and controller components, demanded careful study of both the firmware source code and control-theoretic principles. This knowledge transfer was achieved through a combination of theoretical study and practical validation. The development of multiple simulation environments allowed the team to verify understanding of complex concepts such as rotational filtering, frequency response estimation and closed-loop transfer function calculation before applying them to real flight data.

The hands-on experience of constructing and tuning an FPV drone proved invaluable for contextualizing the analytical methods. Direct exposure to flight behavior, vibration characteristics and the practical constraints of parameter adjustment provided insights that cannot be obtained from simulation alone. This experience revealed the gap between theoretical controller design and real-world implementation constraints, such as motor saturation limits, propeller-induced vibrations and the nonlinear effects of aerodynamic disturbances.

The migration of core functions from MATLAB to Python represents work in progress. While several fundamental algorithms, including closed-loop calculations and transfer function estimation, have been successfully ported and validated against reference implementations, some functions still exhibit numerical discrepancies that require further investigation. The systematic validation approach developed during this phase, using test data from MATLAB as reference outputs, provides a reliable framework for completing the remaining transfers.

However, certain objectives could not be fully realized within the available timeframe. The automatic extraction of flight data directly from Betaflight Blackbox binary logs remains incomplete. Initial attempts using the open-source blackbox decode tool revealed structural incompatibilities in the output format and numerical differences in the decoded data compared to the Betaflight Explorer reference. While these issues are surmountable, addressing them would have diverted resources from more fundamental aspects of the project. The insights gained during this investigation will inform future development efforts.



\subsection{Next Steps}

Future development will focus on three main areas: extending functionality to additional control loops, completing the Python migration and validating the methods through systematic flight testing.

The feature extension track will introduce offline tuning capabilities for position and altitude hold control loops. These cascaded control structures require more sophisticated identification techniques than the angular rate loops addressed in the current implementation. The analysis must account for the coupling between attitude control and translational dynamics, as well as the influence of aerodynamic effects at different velocities. Implementing these capabilities will require extension of the existing frequency response estimation framework to handle multi-input multi-output systems.

The platform completion track will finalize the migration from MATLAB to Python. This includes resolving the remaining numerical discrepancies in functions such as \texttt{apply\_rotfiltfilt} and \texttt{downsample\_frd}, implementing the missing dynamic filter calculations and developing a consistent testing framework across all library functions. The Python implementation will be validated against multiple flight datasets to ensure robustness across different drone configurations and flight conditions.

The practical validation track will conduct systematic flight tests to verify the accuracy of the offline analysis and the effectiveness of tuned parameters. This validation will compare predicted system behavior from offline analysis with measured closed-loop performance during flight. Particular attention will be given to assessing how well the linear system identification captures the nonlinear dynamics present in aggressive maneuvers. The results of this validation will inform necessary refinements to the analysis methods and guide the development of robustness criteria for the tuning process.

\clearpage

\subsection{Conclusion}

This project successfully established the foundational knowledge and software infrastructure required for development of a comprehensive offline tuning tool for Betaflight-based FPV drones. The restructured codebase provides a maintainable platform for implementing advanced features, while the systematic validation framework ensures consistency between MATLAB and Python implementations. The combination of theoretical study, simulation-based verification and practical flight experience yielded a solid understanding of both the Betaflight control architecture and the real-world constraints of FPV drone operation.

The methods implemented demonstrate that offline analysis based on system identification techniques offers a viable alternative to trial-and-error tuning approaches. Frequency response estimation from chirp excitation data enables reconstruction of control loop dynamics, providing objective metrics for evaluating stability margins, disturbance rejection and tracking performance. However, the transition from analytical capability to practical usability requires further development, particularly in automation of the tuning process and reduction of the control-theoretic knowledge required to interpret results.

The work completed during this project phase positions the bachelor thesis for focused development of additional features. The clear separation between data management, analysis algorithms and visualization components allows parallel development of new features while maintaining code quality. The systematic approach to Python migration provides confidence that the final implementation will maintain numerical accuracy while achieving the accessibility benefits of an open-source platform. Continued validation through flight testing will ensure that the tool delivers reliable performance improvements in real operational scenarios.

\paragraph{Titel}~\\
Betaflight - Offline Controller Tuning

\paragraph{Beschreibung}~\\
Betaflight ist ein Open-Source Projekt, das sich auf die Regelung von FPV Quadcopter spezialisiert hat, dies insbesondere im Bereich von Race-Dronen. Die Firmware wird von einer grossen Community weiterentwickelt und ist auf vielen verschiedenen Hardware-Plattformen verfügbar. Betaflight ist die am häufigsten verwendete Firmware für FPV-Drohnen und wird von vielen Hobbyisten und Profis genutzt.

Für die Flugperformace ist die Qualität der Raten-Regelung von entscheidender Bedeutung. Die Regler sind dafür verantwortlich, dass die Drohne stabil fliegt, Störungen wie Wind und Strömungsabrisse (Prop-Wash) unterdrückt und möglichst agil auf Steuerbefehle reagiert. Die Regler und Filter müssen daher sorgfältig getunt und abgestimmt werden, um eine optimale Flugperformance zu erzielen. FPV Piloten fliegen üblicherweise im ACRO mode, sprich das System ist Ratengeregelt und die Stickinputs des Piloten werden als Sollwerte auf den Ratenregler gegeben. Das Tuning dieser Regler geschieht in der Community im Allgemeinen durch Trial and Error. Das bedeutet, dass die Piloten die Reglerparameter anpassen und dann testen. Dies kann jedoch zeitaufwendig und frustrierend sein, da es oft schwierig ist, insbesondere für Leien, die richtigen Parameter zu finden.

Bereits bestehend ist ein Proof of Concept, welches es ermöglicht die Raten-Regler offline basierend auf einem Messdaten-Modell der Drone zu tunen (basierend auf Chirp-Signal Experiment während dem Flug). Das Projekt soll auf diesem Proof of Concept aufbauen und die Methode des Offline Tunings für die Raten-Regler (Gyro) weiterentwickeln. Ziel ist es, eine vollständige, einfach erweiterbare und sauber implementierte Open-Source Libary zu entwickeln. Dies sowohl in MATLAB als auch in Python. Ausserdem soll für die Python Implementation eine ausführliche Dokumentation mit Beispielen für Anwender erstellt werden (Github Markdown Dokumentation). Das Ziel ist es, dass die Libary von der Community genutzt werden kann. Dies soll dazu beitragen, die Flugperformance der Drohnen zu verbessern und den Piloten eine einfachere Möglichkeit zu bieten, ihre Drohnen zu tunen.
