\section{Summary}

Dieses Projekt befasst sich mit der Entwicklung eines Werkzeugs zur Offline-Abstimmung von Gyroskop-Reglern für FPV-Racing-Drohnen auf Basis der Open-Source-Flugsteuerungssoftware Betaflight. Die Qualität des Gyro-Regelkreises beeinflusst direkt die Flugstabilität, die Unterdrückung von Störungen wie Propwash sowie die Wendigkeit der Drohne. Bisher erfolgt die Abstimmung der Drehraten-Regler meist durch zeitaufwendiges Ausprobieren. \par

\section{Abstract}
This project focuses on the development of a tool for offline tuning of gyro controllers for FPV racing
drones based on the open-source firmware Betaflight. The quality of the gyro control loop has a direct influence
on flight stability, the suppression of disturbances such as prop wash, and the agility of the drone. Until now,
rate controller tuning has mostly been performed through time-consuming trial and error. \par
The aim of the project is to develop a modular, open-source solution for offline tuning based on an existing
proof of concept. The code will be implemented in MATLAB, accompanied by a lightweight Python version, and
supplemented with detailed Markdown documentation and examples on GitHub. The project aims to provide the
community with a simple way to efficiently optimise drone parameters and thereby improve flight performance.
\par
The results will be published in a public GitHub repository and documented in a report. In addition to the
software development, the project also includes practical work with FPV drones to validate the developed
methods.

\section{Introduction}
First-person-view (FPV) racing drones require precise and responsive control to achieve high flight stability, minimize disturbances such as prop wash, and maintain agility during rapid manoeuvres. Proper tuning of the rate controllers is key to this performance, as it directly determines how the drone reacts to pilot inputs and external influences.
Until now, tuning these controllers has mainly relied on iterative trial-and-error methods, a process that is both time-consuming and difficult to perform, especially for less experienced pilots.\par
Betaflight, an open-source firmware widely used in the FPV community, provides a flexible platform for configuring flight controllers. However, despite its popularity, efficient tuning remains a challenge. To address this, our project builds upon an existing proof of concept for offline tuning of rate controllers using flight data and system identification techniques. The goal is to transform this concept into a robust, modular, and open-source library that simplifies the tuning process.\par
The library will be implemented in `MATLAB and Python`, offering tools for analyzing flight logs, estimating system dynamics, and optimizing controller parameters without requiring repeated flight tests. A documentation is created, which shows how to use the tool and will be published on GitHub to ensure accessibility for the FPV community. \par
Besides software development, the project involves also building an FPV drone and testing and confirm the effectiveness of the proposed methods. By providing a structured, data-driven approach to tuning, this work aims to improve flight performance and reduce the barriers to achieving optimal control settings for both hobbyists and professionals.

\subsection{Initial situation}
The open-source firmware Betaflight is the most widely used platform for FPV racing drones and is continuously developed by a large community. The quality of the rate control is crucial for flight performance, as it enables stability, agility, and effective suppression of disturbances such as prop wash.\par
Today, tuning of controller parameters is still largely performed by trial-and-error adjustments, a method that is time-consuming and often challenging for less experienced pilots. A proof of concept (developed by Michael Peter) already exists, which enables offline tuning of rate controllers using flight measurement data obtained from chirp signal excitation. However, the current implementation is based on MATLAB, which is not widely used within the FPV community and therefore limits accessibility. In addition, the proof-of-concept requires a certain level of technical knowledge to operate, which further complicates its practical use for many pilots. \par
As a result, the potential of data-driven controller tuning remains largely unused in everyday FPV practice. This creates a gap between academically established system identification and control design methods on the one hand, and the predominantly experience-based tuning approaches used by pilots on the other. Bridging this gap represents a key motivation for the further development of the existing proof of concept.

\subsection{Task and Objective}
The aim of this project is to further develop the existing proof of concept into an accessible and practical tool for tuning rate controllers on Betaflight-based FPV drones. The focus lies on transforming the prototype from a research-oriented MATLAB implementation into a solution that can be used by the wider community with minimal technical barriers. This includes designing a clean and modular software architecture, improving usability, and integrating functions for importing, processing, and analysing flight data.
\par
In addition, the tool will be accompanied by comprehensive Markdown documentation, including explanations of key methods, usage instructions, and practical examples to support new users. The implementation will serve as a foundation for future developments, such as extended analysis features, alternative controller designs, or deployment in other embedded flight control systems. The overarching objective is to provide a reliable, data-driven workflow that replaces subjective trial-and-error tuning and enables verifiable control performance improvements.

\section{Theory}

\subsection{Control System and Signal Processing}
This section provides an overview of the key concepts and methods used for the analysis and tuning of the Betaflight flight controller. It introduces the essential aspects of signal processing, control system identification, and evaluation techniques that form the basis for optimizing controller performance. For a more detailed discussion of the theoretical background and mathematical derivations, the reader is referred to the comprehensive \href{https://github.com/InsaneBroccoli/bf_controller_tuning/tree/PA_final/markdown}{documentationl} available in the GitHub repository.

\subsubsection{Betaflight Gyro Control System}

Based on the Betaflight source code, the gyro control system was reconstructed to obtain a detailed internal representation of the controller structure. This reconstruction forms the basis for the analysis, as it allows a clear understanding of how measured signals propagate through the control loops and how individual controller components influence the system dynamics.

For clarity, the control architecture is illustrated in a simplified form in Figure~xx. The actual implementation includes additional signal paths, filters, and controller elements that are not explicitly shown. Nevertheless, the simplified representation captures the essential structure required for analysis.

The control system consists of two nested loops: an inner loop responsible for angular rate control based on gyroscope feedback, and an outer loop performing angle control based on pilot stick inputs. Both loops incorporate filtering and control elements that directly affect the frequency response and stability characteristics of the system.

By explicitly modeling this structure, measured input and output signals can be assigned to the correct locations within the control system. This is a prerequisite for meaningful frequency response estimation, controller tuning, and the correct interpretation of experimental flight data.

\subsubsection{Chirp Concept}
A chirp is an input signal that sweeps continuously over a defined range (e.g. from a low frequency to a high frequency).
This signal excites the system on multiple frequencies in one run and thus lets you observe the frequency response and step response,
the foundation of controller tuning.
Mathematically, a chirp signal can be represented as a sinusoidal wave with instantaneous frequency that varies linearly or exponential with time. \parencite{bf_chirp}.

\begin{figure}[H]
	\centering
	\includegraphics[width=1.0\textwidth]{./Images/chirp_signal.jpg}
	\caption{Chirp Signal example}
	\label{fig:chirp}
\end{figure}

\subsubsection{Chirp on a drone}
In the context of tuning a drone's flight controller, an exponential sweep is used.
This is due to the dominant low-frequency dynamics, where low frequencies exhibit more predictable responses,
allowing the sweep to allocate more time to higher frequencies for better resolution of system behavior. Additionally,
multirotor vibration resonances are typically spaced logarithmically,
making exponential sweeps more suited for efficient excitation across the frequency range.

The process involves these steps:
\begin{enumerate}
	\item Signal Injection: The chirp signal is added to the pilot's stick input. This composite signal becomes the setpoint for the PID controller.
	\item System Response: The drone attempts to follow this rapidly changing setpoint. The motors react, and the drone will oscillate at varying frequencies corresponding to the chirp signal.
	\item Data Logging: While the chirp is active, high-resolution data from the gyroscope and the motor outputs are recorded using Betaflight's Blackbox feature. This data captures how the drone responds to the control inputs at different frequencies.
\end{enumerate}
\vspace{1em}

The recorded log file, containing the input chirp and the corresponding gyroscope output,
is then used for offline analysis to determine the frequency response of the system.


\subsubsection{Data Import and Preprocessing}
To analyze Betaflight Blackbox logs effectively, the recorded data must first be imported and preprocessed. This process ensures that the raw flight data is correctly scaled, structured, and suitable for further analysis. Each log consists of a header containing essential metadata, such as filter settings and PID values, and a data block with the recorded signals. Both components are required to correctly interpret the flight data.

To reduce computational effort, the raw CSV log files are converted into the faster MATLAB \texttt{.mat} format, allowing for significantly shorter loading times. During this step, signal names are automatically mapped to their corresponding data columns, which simplifies the identification and use of individual signals in future analyses. Betaflight’s High Resolution Mode scales selected signals by a factor of ten to optimize storage and reduce numerical rounding errors. These signals are therefore rescaled to their original values during preprocessing to ensure accurate results.

Finally, the time information, originally stored as a microsecond counter, is converted into a uniform time base. This step includes checking for irregular sampling intervals caused by dropped frames or variations in the effective sampling rate. Proper handling of the time data is essential for reliable frequency analysis and controller tuning.


By checking the time differences between samples, logging issues such as dropped frames or small changes in the sampling rate can be detected.
Correct time handling is essential for all later analysis steps, such as frequency calculations or controller tuning. \parencite{bf_UnshigRes}.

\subsubsection{Estimation of Frequency Response Including Rotational Filtering}

To estimate the frequency response of a system from measured input and output signals, the data must first be transformed into the frequency domain. This is achieved using the Fast Fourier Transform (FFT). The frequency response is then obtained by dividing the Fourier transform of the output signal by that of the input signal:

\begin{equation}
G_{xy}(\omega) = \frac{\mathrm{FFT}(y)}{\mathrm{FFT}(x)} .
\end{equation}

In practical applications, measurement data is often contaminated by noise, which can significantly distort the frequency response estimation. As illustrated in Figure~xx, noise is added to the system between the input signal \(u(t)\) and the output signal \(y(t)\). This noise may originate from sensor inaccuracies, environmental disturbances, or electronic interference. If not properly handled, it can lead to unreliable or misleading results. To mitigate this effect, the program applies a dedicated filtering routine, implemented in the function \texttt{apply\_rotfiltfilt}.

\begin{figure}[h]
\centering
\includegraphics[width=0.7\textwidth]{Images/Freq_Blockschalt.png}
\caption{System model including measurement noise}
\label{fig:system_noise}
\end{figure}

To improve the robustness of the frequency response estimation, a rotational filtering approach is used. In this method, the output signal is shifted to the baseband, filtered, and then shifted back to its original frequency range. The frequency shift is achieved by multiplying the signal with a complex exponential corresponding to the instantaneous chirp frequency:

\begin{equation}
y_{\mathrm{rot}}(t) = y(t) \cdot e^{-j 2 \pi f_{\mathrm{chirp}}(t) t} .
\end{equation}

After shifting the signal to baseband, a zero-phase filter is applied to remove unwanted frequency components while preserving the phase information of the signal. This step is essential for reducing noise without distorting the underlying system dynamics. The filtered signal is then shifted back to its original frequency range.

Subsequently, the frequency response is estimated using the filtered output signal within the function \texttt{Estimate Frequency Response}. The signal is divided into overlapping segments, as illustrated in Figure~xx. A Hann window is applied to each segment to reduce spectral leakage. The FFT is computed for each windowed segment, and the resulting spectra are averaged to obtain a smooth and reliable estimate of the frequency response.

\begin{figure}[h]
\centering
\includegraphics[width=1.0\textwidth]{Images/segmentation.png}
\caption{Segmentation of a signal into overlapping windows}
\label{fig:segmentation}
\end{figure}

\subsubsection{Transfer Function Estimation}

In a closed loop control system, the plant is the physical system that we want to control, for example the movement of a drone.  
To tune a controller, we need to understand how the plant behaves. However, when the system is running in closed loop, this becomes difficult.  
The output is fed back through the controller and continuously changes the input signal. Because of this, the input is no longer an independent excitation, but already contains the controller reactions and disturbance effects.

If we try to measure the transfer function directly from input to output in this situation, the result will not represent the true behaviour of the plant.  
Instead, it will show a combination of the plant dynamics, the controller dynamics and the feedback loop.  
Figure~\ref{fig:closedloop} shows a simplified closed loop structure.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{Images/Control_Loop_easy.png}
    \caption{Simplified closed loop system}
    \label{fig:closedloop}
\end{figure}

To overcome this problem, we use the known relationships between the different transfer functions in the closed loop.  
From the measurement data we compute

\begin{equation}
    G_{yr}(\omega) = \frac{\mathrm{FFT}(y)}{\mathrm{FFT}(r)} 
    = \frac{C(\omega)\,P(\omega)}{1 + C(\omega)\,P(\omega)},
\end{equation}

\begin{equation}
    G_{ur}(\omega) = \frac{\mathrm{FFT}(u)}{\mathrm{FFT}(r)} 
    = \frac{C(\omega)}{1 + C(\omega)\,P(\omega)}.
\end{equation}

By dividing the two expressions, the controller cancels out and we obtain an estimate of the plant transfer function:

\begin{equation}
    P(\omega) = \frac{G_{yr}(\omega)}{G_{ur}(\omega)}.
\end{equation}

This allows us to reconstruct the plant transfer function \(P(\omega)\) from closed loop measurement data without opening the control loop during the experiment.  


\subsubsection{Closed-Loop Calculation}

After determining the plant transfer function, the next step is to analyze the behavior of the overall system when a controller is applied. This is achieved by evaluating the closed-loop transfer functions, which describe the system response, disturbance sensitivity, disturbance rejection capability, and the required controller effort. These measures provide valuable insight into the stability, robustness, and performance of the controlled system.

As an example, the closed-loop configuration shown in Figure~xx is analyzed.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\textwidth]{Images/Control_Loop_easy.png}
    \caption{Simplified closed loop system}
    \label{fig:closed_loop}
\end{figure}

The closed-loop transfer function from the reference input to the output is given by
\begin{equation}
G_{yr}(\omega) = \frac{C(\omega) P(\omega)}{1 + C(\omega) P(\omega)} .
\end{equation}

The sensitivity function, which describes how sensitive the system output is to disturbances and model uncertainties, is defined as
\begin{equation}
S(\omega) = \frac{1}{1 + C(\omega) P(\omega)} .
\end{equation}

The compliance function, representing the system response to disturbances acting on the plant, is given by
\begin{equation}
CC(\omega) = P(\omega) \cdot S(\omega) .
\end{equation}

Finally, the controller effort describes the influence of the reference input on the controller output and is defined as
\begin{equation}
SC(\omega) = C(\omega) \cdot S(\omega) .
\end{equation}

\subsubsection{Compensation of the I-Term} 
The integral term of a PID controller is used to compensate for steady-state errors by integrating the control error over time. In flight control systems, this helps to counteract constant disturbances such as motor imbalances or aerodynamic effects. During fast stick movements or aggressive maneuvers, however, the integral term can accumulate too much error.

In these situations, the accumulated I-term no longer represents a disturbance but instead opposes the intended motion. When the maneuver ends, this can lead to overshoot, bounce-back effects, or slow settling of the system.

To reduce these effects, Betaflight uses a feature called I-Term Relax. This mechanism temporarily limits the integration of the I-term when rapid changes are detected. Depending on the configuration, these changes are identified either from the control setpoint or from the measured gyroscope signal. When the detected change exceeds a defined threshold, the I-term integration is reduced or paused.

This allows the controller to respond quickly to fast pilot inputs while preventing excessive buildup of the integral term. During slower movements and steady operation, normal integration is restored. As a result, I-Term Relax improves flight behavior by reducing overshoot and bounce-back while maintaining good disturbance rejection.

For analysis and controller tuning, the effect of I-Term Relax must be considered, as it modifies the controller behavior depending on the current flight conditions.
\begin{figure}[h]
\centering
\includegraphics[width=0.6\textwidth]{Images/Control_Loop_Iterm.png}
\caption{Segmentation of a signal into overlapping windows}
\label{fig:segmentation}
\end{figure}

In the implemented analysis framework, the I-Term Relax algorithm itself is not explicitly reconstructed. Instead, its overall effect is captured by comparing the analytically modeled controller transfer function with the controller transfer function estimated from measurement data.

To this end, a compensation factor is defined as the ratio between the measured PI controller transfer function and its analytical counterpart:
\begin{equation}
C_{\mathrm{PI,com}}(\omega) = \frac{C_{\mathrm{PI}}(\omega)}{C_{\mathrm{PI,ana}}(\omega)} .
\end{equation}

This frequency-dependent compensation factor represents the combined influence of effects that are not explicitly modeled, including the impact of I-Term Relax. The factor is subsequently applied to both the original analytical PI controller and the newly designed PI controller:
\begin{align}
C_{\mathrm{PI,ana,new}}(\omega) &= C_{\mathrm{PI,ana}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega) , \\
C_{\mathrm{PI,new,new}}(\omega) &= C_{\mathrm{PI,new}}(\omega) \cdot C_{\mathrm{PI,com}}(\omega) .
\end{align}

The resulting compensated controller transfer functions are then reinserted into the closed-loop system for further analysis and evaluation.

\subsubsection{Simulation PID Controller}
To get a better understanding of the individual controller components, we wrote an additional MATLAB script that lets us combine different controller types with simple plant models. The user can switch between P, I, PI, PD, and PID controllers, as well as between a few basic plant types. This makes it easier to see how each controller part affects the overall system behaviour. The script calculates the open-loop and closed-loop transfer functions and produces Bode plots, Nyquist diagrams, and step responses. Figure~\ref{fig:controllerbode} shows an example Bode plot from this simulation.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=1.0\textwidth]{./Images/Controller_Bode.png}
	\caption{Bodeplot out of Controller Simulation}
	\label{fig:controllerbode}
\end{figure}

The frequency response of the shown PID controller is based on the parameters 
$K_p = 100$, $K_i = 10$ and $K_d = 10$. 
The proportional gain defines the magnitude level in the mid-frequency range:
\[
20\log_{10}(K_p) = 20\log_{10}(100) = 40\,\text{dB}.
\]

The integral term causes the slope of $-20\,\text{dB/decade}$ at low frequencies with
\[
|C_I(j\omega)| = \frac{K_i}{\omega} = \frac{10}{\omega}.
\]
The corresponding lower corner frequency is
\[
\omega_{k,I} = \frac{K_i}{K_p} = \frac{10}{100} = 0.1\,\text{rad/s}.
\]

The derivative term causes the slope of $+20\,\text{dB/decade}$ at high frequencies with
\[
|C_D(j\omega)| = K_d\,\omega = 10\,\omega.
\]
The corresponding upper corner frequency is
\[
\omega_{k,D} = \frac{K_p}{K_d} = \frac{100}{10} = 10\,\text{rad/s}.
\]

This example also shows that changing the integral and derivative gains shifts the position of the slopes in the Bode plot. A larger integral gain moves the low-frequency slope towards higher frequencies, while a larger derivative gain moves the high-frequency slope towards lower frequencies. In this way, the shape of the frequency response can be adjusted to the desired system behaviour.

\subsection{The tuning process using our tool}

\colorbox{yellow}{overview plots}

\subsubsection{filter tuning}
Before we start tuning the PID controllers, we need good filtering, to have clean signals to work with. The general aim here is to use as little filtering as possible, because too much filtering causes delay in the system. However no quadrocopter build is perfect, so at least some filtering is always necessary in order to get a good tuned system.

To do this we started to look at the spectrograms and the spectra figures first, after the import of a log file into MATLAB. By comparing the filtered and unfiltered plots, you can see how well the current settings filter out unwanted vibrations.

Further Information about Spectra and Spectrograms can be found 
\href{https://github.com/InsaneBroccoli/bf_controller_tuning/blob/PA_final/markdown/Spectrum_Spectogram}{here}.

The \textbf{spectra} in Figure~\ref{fig:Spectra_tuning} shows the frequency composition of the gyro signals. 
Peaks in this plot point to vibration sources at specific frequencies.
When we analyze this plot, we look for three main things: 
\begin{itemize} 
  \item \textbf{Resonance Peaks:} If all three axes show a peak at the same frequency, it usually means there is a resonance in the frame or because of a poorly fixed component. This can be fixed with a specific notch filter.
	\item \textbf{Noise:} A high noise level indicates general vibration issues. Clean lines in the plot show, that the filtering is working well. 
	\item \textbf{Axis Sum:} The axis-sum shows the overall vibration level across all gyro axes. A properly filtered signal drops quickly after the motor frequencies (around \colorbox{yellow}{xx} Hz) and remains low, indicating effective suppression of high-frequency noise and resonances.
\end{itemize} 

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{./Images/Tuning_OvershootExpress/Spectra.jpg}
  \caption{Spectra}
  \label{fig:Spectra_tuning}
\end{figure}

The vibrations are also visible in the \textbf{spectrogram} plots in Figure~\ref{fig:Spectrograms_tuning}. 
Here frequencies are plotted against thrust level and the color show the signal intensity. Red equals high energy and blue low energy.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{./Images/Tuning_OvershootExpress/Spectrograms.jpg}
  \caption{Spectrograms}
  \label{fig:Spectrograms_tuning}
\end{figure}

\textbf{Vertical lines} in the spectrogram indicate vibrations at fixed frequencies that do not change with thrust. These usuallly come from frame resonances or loose components. Such resonances can be removed with static notch filters, but because they sit only on a single frequency, they must be used carefully. For more robust suppression, especially when frequencies shift due to bent props or changing load conditions, a dynamic notch filter is usually the better choice.

\textbf{Diagonal lines} show vibrations that change with motor speed, such as propeller noise. Using the RPM Filter, these propeller vibrations can be filtered out quite well. This filter uses real time RPM telemetry data to place notch filters exactly on fundamental and harmonic frequencies of each motor. As propeller vibrations are directly proportional to motor RPM, this approach eliminates noise at its source instead of relying on fixed or dynamic estimation. We kept the RPM filter with the default settings. We use three-bladed propellers, so three setting the filter to three harmonics should be fine.

\textbf{Aliasing}\\
As we use a 2kHz logging frequency, we have set a PT1 lowpassfilter to avoid aliasing. This can be seen in the Spectrogram as a diagonal lines going down, as you move to higher frequencies. The cutoff frequency should not be larger than the sampling frequency divided by two. To be on the safe side we set it to 800Hz.

\textbf{Dynamic notch filter}\\
The dynamic notch filter automatically finds and removes mechanical motor noise with the highest amplitude for each axis. The standard setting here is 2 notches from 100 to 600 Hz. As it is seen in Figure~\ref{fig:Spectrograms_tuning}, the filtered plots still have rather high oscillation amplitudes. To filter these out we increased the Notch count from two to three.

\textbf{D term lowpass filter}\\
The D-term in a PID controller amplifies high frequency gyro noise. So this filter controls, how much noise is fed back into the control loop. If too much noise passes through, the D-term causes rapid micro-oscillations in the motors, leading to overheating and potential hardware failure.
For our initial flight, we configured a PT3 (3rd Order) filter with a cutoff of 100 Hz. This because PT3 has a much steeper slope than a standard 1st or 2nd order filter. This allows us to aggressively suppress high-frequency noise while minimizing delay in the lower frequencies, where the actual flight control happens. The 100 Hz cutoff served as a conservative starting point. In further tuning, this value can be increased again to improve responsiveness but keep the motors cool.

\textbf{Yaw lowpass filter}\\
The Yaw Low Pass Filter smooths the gyroscope signal by ignoring high-frequency noise. Since the yaw axis typically experiences less mechanical vibration than roll and pitch, the filter can often be configured less aggressively without compromising signal quality.
For our setup, we retained the default Betaflight settings, as they provided good noise suppression without creating unnecessary delay.

Consider looking at the \href{https://www.betaflight.com/docs/wiki/configurator/pid-tuning-tab}{Betaflight wiki page} for more information about Betaflight filters.

\subsubsection{PID tuning}
After the filter settings were set, we could move on to the PID tuning.

The tool calculates the Plant and Controller Bode plots to build a mathematical model of the drone. These are exciting for an engineer, but not necessarily useful for a user in the community, as they are less intuitive. We mainly focused on the Step Response and the Gang of Four, where you can see flight performance and stability directly.

The \textbf{step response} plot shows exactly what happens when the pilot moves the stick rapidly. You can see how fast the drone reacts to the command, if it overshoots the target value, and how quickly it settles to a steady state.

\begin{figure}[H]
	\centering
	\includegraphics[width=1.0\textwidth]{./Images/Tuning_OvershootExpress/Step_response_pitch_tuned.jpg}
	\caption{Step Response}
	\label{fig:step_response_tuning}
\end{figure}

\begin{itemize} 
  \item Tracking (Top Plot): It shows how the drone follows a command
	\item Compliance (Bottom Plot): This shows how the drone reacts to external hits, like wind
\end{itemize}

\textbf{Gang of Four}\\
The Gang of Four is a standard set of four transfer functions that together fully characterize a feedback control system. These four plots show the Sensitivity (S), Complementary Sensitivity (T, Bode plot), Controller Effort (SC), and Compliance (SP). By looking at these plots, we can see if the drone is stable, how well it follows commands, how it handles wind, and whether the motors are working too hard—all in one view.

During our tuning, we paid specific attention to three of these plots: 
\begin{enumerate} 
	\item Sensitivity (S): 
  It shows how the system responds to noise and reference commands. The peak value tells us how stable the system is. For a well-damped system, the peak should be below 6 dB, because higher values mean the drone could start oscillating or become unstable.
	\item Controller Effort (SC): 
  Indicates how hard the controller is working. If the effort is too high at high frequencies, the system is reacting to sensor noise rather than real disturbances. This causes unnecessary motor activity, leading to heating and wear.
	\item Compliance (SP):
	Shows how much external disturbances (like wind gusts) affect the drone's motion. A lower compliance is better, it means the drone resists disturbances more effectively.
\end{enumerate}

\begin{figure}[H]
	\centering
	\includegraphics[width=1.0\textwidth]{./Images/Tuning_OvershootExpress/gang_of_four_pitch_tuned.jpg}
	\caption{Gang of four}
	\label{fig:gangoffour_tuning}
\end{figure}

\textbf{PID tuning summary}
Our tuning objective was to achieve a fast step response without overshoot while maintaining good disturbance rejection and stability margins. It is important to note that there is no universally perfect tune—settings depend heavily on pilot preferences. Racing pilots typically prefer aggressive, responsive tuning for competitive performance, while freestyle pilots prioritize smoothness and flight feel. Since none of our team members is a professional pilot, we focused on achieving robustness and a step response without overshoot. This tuning approach is probably somewhere between of what a racing pilot would want and a freestyle pilot. Robustness in this case is practical, because scenarios like slightly bent propellers, a battery positioned off-center, or additional components such as cameras mounted on the drone can be handled.

The tuning process involved iteratively adjusting PID gains while monitoring both the step response and Gang of Four plots side by side. We found and used an online \href{https://www.luisllamas.es/en/pid-controller-simulator/}{PID simulator} as a guidance tool to build intuition for how P, I, and D values affect system behavior. 
For the step response, we aimed for a fast rise time with minimal or no overshoot and a smooth curve without oscillations. On the Gang of Four side, we wanted the sensitivity peak to stay below 6 dB for good stability margins, low compliance across the control bandwidth for effective disturbance rejection, and reasonable controller effort to avoid amplifying sensor noise. All transfer functions should show smooth, rounded shapes without sharp resonances that indicate problematic dynamics.

Achieving an optimal tune required several iterations due to challenges with filter adjustments and occasional logging issues. Nevertheless, the drone was successfully tuned, and the improvement was immediately noticeable. During propwash maneuvers, the drone remained significantly more stable, and flips were executed with greater precision at the stop point.

\subsection{Decoding Betaflight Blackbox Logs}
\subsubsection{Purpose}
Currently to obtain a useable Blackbox log from Betaflight, pilots rely on the Betaflight Explorer. 
Wich is a reliable tool, but lacks comfort if the tuning tool is used iteratively since you have to visit the Explorer every time you want to download a new log.
To improve this workflow, we tried to make use of the existing open-source blackbox\_decode tool.

\subsubsection{\href{https://github.com/betaflight/blackbox-tools/}{blackbox\_decode tool}}
The blackbox\_decode tool is a C-based command-line utility designed to convert Betaflight Blackbox log files from their proprietary binary format into more accessible formats such as CSV.
It offers similar core functionality to the Betaflight Blackbox Explorer but is intended for users who prefer command-line tools or need to automate log processing tasks.\par

However, integrating blackbox\_decode into our project presented several challenges.
The most obvious issue is the absence of header information by default. 
While this can be addressed by using the --save-headers flag, the format of these headers differs from that used by the Betaflight Explorer. 
This discrepancy is manageable, as we could adapt our data import functions to handle both formats.\par

A more significant problem is the presence of numerical differences in the decoded data.
When comparing logs decoded with blackbox\_decode to those processed with Betaflight Explorer, the resulting datasets differ structurally and semantically in several critical ways.
Specifically, the blackbox\_decode stores the vehicle attitude as Euler angles in degrees, whereas the Explorer provides quaternion-like components. 
With priority set on other tasks, we decided to set aside the integration of blackbox\_decode for now.

\subsection{Conversion from MATLAB to Python}

To make the project more accessible to the FPV community, we decided to migrate the existing MATLAB codebase to Python.  
The first step was to select suitable Python libraries that offer similar functionality to MATLAB, while maintaining code efficiency and readability.  
After evaluating several options, we chose the following libraries:  
\begin{itemize}
  \item \textbf{NumPy}: For numerical operations and array manipulations, analogous to MATLAB's matrix operations.
  \item \textbf{SciPy}: For scientific computing tasks, including signal processing functions comparable to MATLAB’s capabilities.
  \item \textbf{Matplotlib}: For plotting and visualization, providing features similar to MATLAB's plotting tools.
  \item \textbf{Pandas}: For data manipulation and analysis, useful for handling tabular data as in MATLAB tables.
  \item \textbf{Control Systems Library (control)}: For control system analysis and design, offering functions equivalent to MATLAB's Control System Toolbox.
\end{itemize}
We selected Python version 3.12, as it is well-supported and compatible with the required libraries.  
To validate these choices, we developed a prototype script that implements the core functionalities needed for the Drone Tuning Tool.  
The script loads flight log data from CSV files, parses and caches the data efficiently, and extracts relevant signals such as setpoints and gyro measurements.  
NumPy and Pandas are used for numerical and tabular data handling, while SciPy provides signal processing utilities for windowing and frequency analysis.  
The Control Systems Library is employed to estimate the system’s frequency response and step response from flight data, replicating MATLAB’s identification routines.  
Matplotlib is used for visualizing raw signals, chirp responses, and system characteristics.  
The modular structure, including custom data classes and caching, ensures fast and reproducible analysis.  
This approach demonstrates that Python and its scientific libraries are suitable replacements for MATLAB in the drone tuning workflow.  
While Pandas is not strictly necessary for the prototype, it simplifies data handling and improves code readability.  
However, to minimize dependencies and ensure cross-platform compatibility, we may consider removing Pandas in the final implementation.  
The flexibility of Python also allows for easier integration with other tools and automation of data processing tasks, which is beneficial for large-scale log analysis.  

\subsection{Python in MATLAB}

In our initial porting attempt, we utilized MATLAB’s built-in functionality to execute Python code directly from within the MATLAB environment.  
While this approach allowed us to access Python libraries and scripts, it introduced some challenges.  
One major issue was the frequent need for unit conversions between MATLAB and Python data types, which often led to subtle bugs and inconsistencies.  
Additionally, we encountered differences in the implementation of certain algorithms, such as varying scaling conventions in the state-space representation of transfer functions.  
These discrepancies complicated the integration process and made it difficult to ensure consistent results across both platforms.  
Managing library dependencies and Python environments within MATLAB also proved cumbersome, especially when working across different operating systems or MATLAB versions.  
As a result, this method proved unreliable for our project’s requirements.  
We ultimately decided to pursue a native Python implementation to avoid these integration issues and streamline the development workflow.  

\subsection{Transferring the MATLAB Library to Python}

The core functionality of the Drone Tuning Tool resides in its library functions.  
To ensure that the Python implementation is both reliable and consistent with the original MATLAB code, we systematically transferred each library function from MATLAB to Python.  
For functions with simple numerical outputs, we used \texttt{np.testing.assert\_allclose} with appropriate absolute and relative tolerances, saving the function inputs and outputs from MATLAB and comparing them with the Python implementation.  
For more complex functions, such as those involving state-space outputs, we developed dedicated test scripts to compare the behavior of the MATLAB and Python versions across a range of scenarios.  
This rigorous testing approach helped us validate the correctness and consistency of the ported library functions.  
Automated testing and comparison between MATLAB and Python outputs were essential to ensure that the new implementation maintained the expected performance and accuracy.  
This systematic transfer and validation process significantly reduced the risk of introducing errors during migration and increased confidence in the reliability of the Python-based tool.

\section{Results}
Throughout the project, we achieved a range of practical and technical results. The most important outcome was gaining a deep understanding of the Betaflight control system, including how its filter structures and controller components interact to stabilise the gyro control loop. In addition, we developed a solid foundation in the application of essential signal-processing methods and learned how to use them correctly for frequency-domain analysis, step-response estimation and data preparation. This newly acquired knowledge will be crucial for the further development of the tool and forms an important basis for the work that will follow in the bachelor’s thesis. The simulations carried out during the project helped us link theoretical concepts to the real dynamic behaviour of an FPV drone and validate our understanding of the control loops. \par
Alongside the theoretical work, we also built and configured an FPV drone from scr atch and performed flight tests and tuning. This hands-on experience provided valuable insight into the practical challenges of drone construction, setup, flight and tuning. It helped us better understand the real-world implications of our analysis, the needs of the FPV community, and ultimately strengthened the connection between theory and practice. \par
On the software side, we restructured the existing prototype into a modular codebase, created comprehensive Markdown documentation on GitHub, and began transferring key functions from MATLAB to Python to enable future extensions. We also gained experience in object-oriented programming and code organisation for larger projects. In addition, we made significant progress in migrating core functions from MATLAB to Python, such as closed-loop calculations and transfer-function estimation. Although the full transfer is still ongoing, the results achieved so far provide a strong foundation for further development and refinement during the bachelor’s thesis.\par
A particularly time-consuming part of the project was the development of an automatic extraction method for flight data directly from Betaflight Blackbox logs. Despite testing different approaches, we were not able to complete a reliable solution within the given time frame. However, the insights gained during this process form a valuable basis for further investigations, and we plan to revisit this topic as part of the bachelor’s thesis. \par
In summary, the project demonstrates that offline analysis and tuning of Betaflight-based FPV drones provides a robust, objective and data-driven approach to optimising flight performance. The implemented methods enable the reconstruction of control-loop behaviour from flight measurements, allowing for a detailed understanding of system dynamics and the impact of controller settings. The work carried out so far lays a solid foundation for the bachelor’s thesis, during which the tool will be extended with additional tuning capabilities, fully migrated to Python, and validated through further flight tests.
